# 레이어 5 · 행동 · 프롬프트 (프롬프트)

모두 설치형 소스가 없는 "작성 기법"입니다. 디자인 작업 지시서(brief.md)나 CLAUDE.md를 쓸 때 템플릿으로 쓰세요.

## 29. system-structure — 명확한 프롬프트 구조
```
## 역할
## 목표 (완료되면 무엇이 참이 되는가)
## 입력 자료 (파일 경로)
## 제약 (반드시 / 절대 금지)
## 산출물 (형식, 경로, 파일명)
## 완료 기준 (검증 방법)
```

## 30. persona-architecture — 성격과 말투의 범위 설정
```
이 제품의 목소리를 정의해 줘: 성격 형용사 3개, 반대로 절대 아닌 것 3개,
상황별(환영/오류/성공/빈 상태) 예시 문구 각 2개. 결과를 voice.md로 저장.
```

## 31. tone-calibration — 격식부터 친근함까지 톤 조정
```
같은 문구를 톤 1(공식) ~ 5(친근) 다섯 단계로 써 줘. 이 제품은 <N>단계를 기본으로 하고,
오류·결제·보안 관련 문구는 한 단계 더 격식 있게.
```

## 32. emotional-design — 갈등·불편 상황 완화
```
결제 실패, 데이터 손실 위험, 권한 거부, 대기 지연 상황의 화면과 문구를 설계해 줘.
원칙: 사과는 짧게, 원인은 사용자 탓 없이, 다음 행동은 버튼 하나로, 불안을 줄이는 상태 표시(저장됨, 재시도 중).
```

## 33. template-design — 매개변수형 중괄호 템플릿
```
디자인 요청 템플릿:
{{화면}}을 {{대상 사용자}}를 위해 만든다. 핵심 행동은 {{주요 CTA}}.
스타일은 {{레퍼런스}}의 {{참고할 점}}만 가져오고 {{피할 것}}은 피한다.
산출물: {{형식}} → {{경로}}
```

## 34. few-shot-patterns — 예외 사례를 담은 예시 패턴
```
좋은 예 2개와 나쁜 예 1개를 함께 줄게. 나쁜 예가 왜 나쁜지 먼저 설명하고, 좋은 예의 공통 규칙을 뽑아 그 규칙으로 작업해.
[좋은 예 1] ... [좋은 예 2] ... [나쁜 예] ...
```

## 35. chain-of-thought — 단계별 추론 흐름 추적
```
바로 만들지 말고 먼저: 1) 사용자와 목표 정리 2) 정보 위계 결정 3) 레이아웃 후보 2개 비교
4) 하나 선택한 이유 를 plan.md에 쓰고, 그다음 구현해.
```

## 36. constraint-spec — 엄격한 출력 형식 제한
```
출력 제약:
- 단일 HTML 파일, 외부 CDN은 지정한 것만
- 색은 tokens.css 변수만, 임의 HEX 금지
- 폰트 2종 이하, 그림자 2단계 이하
- 결과 외 설명 문장 출력 금지
```
